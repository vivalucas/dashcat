## 事实与文档分工

当前约定直接更新，过期内容可删除；重要原因和经验留 11，完整修改历史交给 Git，不另写开发流水账。未解决问题、未提交且无法恢复的工作必须保留。

代码说明当前实现，确认需求说明预期；发现不一致时先判断是文档过期还是 bug。版本以工程配置为准，数据结构以实现和兼容逻辑为准，文档只补充业务语义。根 README 面向使用者，AGENTS 维护核心协作边界，本文件维护导航和流程，CLAUDE 只导入。

## 开发与协作

按入口检查代码、工作区、当前分支和 upstream，明确“需求—现有实现—本轮改动—验证方式”后实施。小修复可直接推进；跨模块、数据结构或长期行为变化先在 09 写精简计划。改变产品含义或破坏兼容的重要取舍先讨论。

多人并行时在 01 登记范围、负责人和依赖；共享文件重叠时协调顺序。登记不是文件锁，不覆盖其他任务的未提交内容。

## Git 与跨设备同步

- 沿用当前分支；未经用户指令不新建/切换分支、不建工作树。
- 提交和推送默认由用户指令触发；普通推送不自动修改版本、打标签或创建 Release。
- 开工检查 `git status --short --branch`、upstream 和远端状态。文档整理不自动合并远端代码。
- 工作区有修改时不自动 stash、reset 或清理。分叉时先识别双方改动并给出方案；不自动 rebase、强推或删除分支。
- “推送 / 收工同步”包含提交本轮归属明确的改动并推送当前分支；推送前 fetch 并再次核对目标。
- `v*` 标签会触发 DMG Release，标签与发行必须有明确授权；细节见 08。

## 日常收尾

逐项核对需求、diff 和关联路径。验证与影响相称：核心数据路径运行回归，UI 改动检查实际入口及空/错/加载/禁用状态，可运行时查看界面；本机构建不代表系统权限交互已验收。

只更新有变化的状态和约定。需要跨对话继续、存在风险或验收缺口时写入 01；普通完成记录留给 Git。最终报告完成内容、验证、限制、当前分支以及实际提交/推送状态。

## 专项评审与上下文维护

全面评审默认只读。报告区分项目理解、确认问题、待验证问题和体验建议；每项给触发条件、位置、影响、证据和优先级。自查不能称独立评审，历史通过不能保证当前版本。

文档出现重复或阶段结束时再集中整理：保留当前约定、未解决问题、活跃交接、用户约束和必要复现信息；已完成计划只提炼长期决策；不确定内容标为待复核。真实密钥、Cookie、密码和敏感剪贴板样本不得进入文档。
